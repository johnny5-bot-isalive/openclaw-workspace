## OpenClaw slowness diagnosis
- Jaret reported OpenClaw felt especially slow after recovery. Startup/bootstrap markdown was checked and was not the main cause: AGENTS/SOUL/USER/MEMORY/TOOLS/HEARTBEAT/OPERATIONS/PROJECT/today-memory totaled about 36 KB.
- Main latency drivers found: current Mission Control session was about 109k tokens, Emily/heartbeat main sessions were also over 100k, and Sammy main was about 170k/200k. Main and Sammy session stores were large (`~446 MB` and `~398 MB`).
- Tool-call latency was also affected by transient `openclaw-hooks relay ... pre_tool_use` workers briefly using >100% CPU; one diagnostic hook-info command got stuck and was cleared. After cleanup, steady-state CPU returned mostly to Codex app servers and gateway.
- Recommended follow-up: compact heavy sessions with `openclaw sessions compact <session-key>` rather than moving workspace bootstrap files; consider whether hook relay/command-logger overhead is an OpenClaw regression if CPU spikes persist.
- Later same-day follow-up after `/new` sessions showed session JSON stores were small again (`main` ~95 KB, `sammy` ~59 KB) and current Mission Control was ~48k tokens, so retained context was not the main live slowdown. The stronger cause was runtime overhead: repeated Codex tool calls spawned multiple hot `openclaw-hooks relay ... pre_tool_use` workers (~240 MB RSS each, often >100% CPU) and gateway diagnostics showed severe event-loop-delay warnings. Source review found the native relay treats absent `tools.loopDetection` as enabled (`config?.enabled !== false`) even though the schema says default false. Set `tools.loopDetection.enabled=false` explicitly and validated config; OpenClaw said gateway restart is required to apply. Approval note: `/mnt/c/Users/Jaret/Obsidian/The Nexus/00 Inbox/OpenClaw Gateway Restart Approval - 2026-07-12.md`.
